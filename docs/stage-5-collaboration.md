# Этап 5 Совместная работа и история встреч

Отчёт описывает реализацию `CODEX_PROMPT_05.md`: зал ожидания, постоянный чат,
вложения, прочтение, поднятые руки, реакции, уведомления, расписание и историю.
Новые возможности используют существующие PostgreSQL, Redis, MinIO и авторизацию.
Передача медиа через SFU и обработка записи в recorder-worker не переписывались.
Этап 6 не реализуется.

## 1 Реализованные возможности

Владелец может запланировать встречу и включить зал ожидания. Участник добавляет
встречу по приглашению в свой список, после начала ожидает допуска и подключается
к медиа только после решения организатора или соорганизатора. Встреча сохраняет
чат, ответы, файлы и отметки прочтения. Доступны поднятие руки, четыре реакции,
личные уведомления и история с состоянием записей. Завершённый чат доступен только
для чтения допущенным участникам, которые не были исключены.

Интерфейс сохраняет дизайн Meet. Добавлены загрузка, повторные попытки, ошибки,
индикатор передачи файла, уведомления, фильтры истории и состояния ожидания.
Одна конференция использует одно WebSocket-соединение; медиаподписчик не заменяется
подписчиками чата и реакций.

## 2 Архитектурные решения

PostgreSQL остаётся источником постоянных данных. Изменения чата публикуются после
успешной транзакции. Redis обеспечивает присутствие, доставку событий, временное
состояние рук и отдельные ограничения частоты запросов. Потерянные события чата
восстанавливаются чтением истории при переподключении и каждые 15 секунд.

Уведомления доставляются по отдельному авторизованному HTTP SSE-потоку, поэтому
работают на главной странице и в зале ожидания без доступа к комнате. Решения о
допуске и готовые записи создают задания в PostgreSQL в той же транзакции через
триггеры. Обработчик формирует уведомления, а `published_at` позволяет повторять
публикацию после сбоя. RabbitMQ продолжает обслуживать существующие команды записи;
продуктовые задания не направляются в очередь recorder-worker.

## 3 Миграции и схема базы

| Миграция | Изменения |
| --- | --- |
| `000012_stage_five_conferences` | Расписание, флаг зала ожидания, admission state и версия решения, индексы истории и очереди ожидания |
| `000013_chat_attachments_read` | `chat_messages`, `chat_attachments`, `chat_read_states`, индексы курсора, непрочитанного и очистки |
| `000014_notifications` | `notifications`, `notification_jobs`, индексы непрочитанных и необработанных заданий, транзакционные триггеры |

Миграции допускают повторное выполнение существующим механизмом запуска проекта.
Отдельная таблица чатов не создаётся: одна конференция соответствует одному чату.
Новые внешние ключи используют `RESTRICT`, а не каскадное удаление истории.
Для `notification_jobs.conference_id` нет избыточного прямого внешнего ключа:
историю защищают связи задания с участником или записью. Это предотвращает
инверсию блокировок между завершением записи и остановкой конференции.

Порядок сообщений задаётся серверным `BIGSERIAL`; уникальный индекс имеет форму
`(conference_id, sequence DESC)`. Отдельный глобальный индекс sequence исключён:
он приводил к сканированию сообщений других конференций. Read state использует
одну строку на пользователя и конференцию, а не строку на каждое сообщение.

## 4 Состояния зала ожидания

| Состояние | Доступ и переход |
| --- | --- |
| `waiting` | Только собственное членство, ограниченные сведения о встрече и личные уведомления; организатор может допустить или отклонить |
| `admitted` | Чат и история по правилам членства; живые медиа требуют `joined` и открытой встречи |
| `rejected` | Нет медиа, чата, файлов и истории; повторный invite не обходит отказ |
| `kicked` | Доступ отозван, подключение закрывается, повторный вход запрещён |

Admission отделён от состояния подключения. Выход ожидающего участника даёт
`left + waiting`; повторный вход восстанавливает тот же запрос и UUID. Переподключение
не создаёт второго участника. Для ожидающих WebSocket-комната не открывается;
решение приходит через SSE и опрос собственного членства раз в 3 секунды.

Допуск разрешён `owner` и `co_host`, которые присоединились к активной встрече.
Обычная модерация не действует на ожидающих: для них есть отдельное отклонение.
Одновременные admit/reject сериализуются блокировкой конференции; повтор одного
решения идемпотентен, противоположное решение после завершённого перехода даёт 409.
Очередь ожидания не входит в снимки и события обычных участников.

## 5 API и протокол чата

Все пути в таблице начинаются с `/api/v1/conferences/:id` и требуют Bearer JWT.

| Метод и путь | Назначение |
| --- | --- |
| `GET /messages?before=cursor&limit=50` | Последние сообщения и следующие страницы истории |
| `POST /messages` | `{clientRequestId,text,replyTo?,attachmentIds?}` |
| `PATCH /messages/:messageId` | Редактирование собственного текста |
| `DELETE /messages/:messageId` | Мягкое удаление своего сообщения; модератор может удалить чужое |
| `GET /chat/read` | Текущий курсор и число непрочитанных |
| `PUT /chat/read` | `{messageId}` — продвижение курсора |

Сообщения содержат UUID, строковый sequence, автора, текст, ссылку ответа,
вложения, версию и временные отметки. Текст — обычный текст, максимум 4000 Unicode
символов. Без текста требуется хотя бы один файл. Ответ должен ссылаться на
существующее сообщение этой же конференции. Страница ограничена 100 сообщениями.

Уникальность `(conference_id,sender_user_id,client_request_id)` предотвращает
дублирование при повторной отправке. Повтор с другим содержимым даёт 409.
Редактирование и удаление используют одинаковый порядок блокировок; удалённый
текст нельзя восстановить запоздалым редактированием.

События: `chat.message.created`, `chat.message.updated`, `chat.message.deleted`,
`chat.read.updated`. Клиент объединяет страницы по UUID и версии, хранит sequence
без потери точности и объединяет обновления запросов в окно 200 мс.

## 6 Вложения и хранение

Последовательность: `POST /attachments/init` → `PUT /attachments/:id/content`
с исходными байтами → `POST /attachments/:id/finalize` → отправка сообщения с ID
файла. Повторная финализация безопасна; повторная передача с другими байтами
отвергается. Файл привязывается к сообщению атомарно.

Допустимы JPEG, PNG, WebP, PDF, TXT и CSV. Ограничения: 10 МиБ на файл, 5 файлов
на сообщение, 20 незавершённых вложений на пользователя в конференции. Сервер
проверяет имя, расширение, MIME, содержимое, размер и SHA-256. Путь генерируется
сервером: `attachments/{conferenceUUID}/{attachmentUUID}/{uploadTokenUUID}`.
В публичный ответ не входят внутренний ключ, токен загрузки и lease.

Одновременно один API принимает не более четырёх файлов; буферы содержат не более
примерно 40 МиБ полезных данных. Nginx пропускает до 11 МиБ на конкретном upload
маршруте, API проверяет точный лимит 10 МиБ. Проксирование запроса потоковое.
Чтение тела ограничено 60 секундами, операция — 75 секундами, lease — 120 секундами.

Незавершённые `pending/ready` истекают через 30 минут. Фоновая очистка раз в минуту
обрабатывает до 100 строк с защитой действующих загрузок и удаляет только точные
серверные префиксы. Привязанный объект сохраняется; проигравшие попытки удаляются.

`GET /attachments/:id/download` повторно проверяет членство и видимость сообщения
и выдаёт ссылку на 5 минут. MinIO остаётся закрытым; публичная политика бакета
приводит к отказу инициализации, а не автоматически переписывается. Ответ скачивания
принудительно `attachment` и `application/octet-stream`, без встроенного просмотра.

## 7 Отметки прочтения

`chat_read_states` хранит последний message ID, sequence и время. Условное
обновление продвигает sequence только вперёд; запоздалая вкладка его не уменьшает.
Непрочитанные считаются по индексированному диапазону, без своих и удалённых
сообщений. UI отмечает прочтение только при видимой странице и последних видимых
сообщениях, с задержкой 800 мс. Запись read state и отправка сообщений имеют
разные лимиты, поэтому частые read updates не блокируют отправку или звонок.

## 8 Руки и реакции

`GET /hands`, `PUT /participants/:participantId/hand {raised}` и
`POST /reactions {emoji}` требуют допущенного участника активной встречи.
Поднять можно только свою руку; организатор может опустить чужую, соорганизатор —
руку обычного участника. Состояние рук находится в Redis, включается в первый
снимок комнаты и переживает переподключение не дольше одного часа. Максимум —
500 записей; недопущенные и вышедшие участники не показываются.

Повторный raise сохраняет исходное время. При доставке событие руки сверяется с
актуальным Redis-состоянием, чтобы запоздалое raise/lower не отменяло более новое
действие. Снимок и периодический запрос исправляют потерянные события.

Реакции ограничены `👍 👏 ❤️ 😂`, не сохраняются в PostgreSQL. Лимит — 5 реакций
за 10 секунд на пользователя; для комнаты — 30 в секунду. Руки имеют отдельный
лимит 10 действий в минуту, чтение рук — 120 запросов в минуту. Проверка допуска
предшествует расходованию общего лимита комнаты.

У Hub отдельная очередь 128 некритичных событий и отдельный обработчик. У каждого
сокета ещё одна очередь на 8 событий чата, рук и реакций. Переполнение отбрасывает
эти восстанавливаемые события, но не закрывает звонок. Signaling, модерация и
состояние записи используют прежнюю очередь с приоритетом. UI показывает не более
шести реакций одновременно, примерно на 3,5 секунды.

## 9 Уведомления

Типы версии 1: `conference.soon`, `admission.decided`, `recording.ready`.
Payload содержит только ссылки и состояние, без текста чата, имён файлов или
ссылок на скачивание. Уведомление не даёт права открыть соответствующий ресурс.

API: `GET /api/v1/notifications?cursor&limit`,
`POST /api/v1/notifications/:notificationId/read`,
`GET /api/v1/notifications/events`. Последний путь — fetch SSE с JWT в заголовке,
не в URL. Поток заканчивается при истечении JWT. На API не более 256 потоков,
на пользователя — 4; попытки подключения ограничены отдельно. Есть heartbeat и
буфер 32 события, список опрашивается каждые 15 секунд для восстановления.

Фоновая обработка выполняется раз в 5 секунд. Напоминание создаётся в пределах
15 минут до встречи. Ключ расписания использует UTC epoch, независимо от timezone
SQL-сессии. Admission jobs сохраняют каждую версию решения, в том числе быстрый
admit → kick. Recording jobs обрабатывают участников порциями по 100 с курсором;
общий бюджет цикла — 1000 получателей. Получатель должен существовать и быть
допущен до готовности записи и сохранять доступ при обработке задания.

Задания выбираются через частичный индекс и `FOR UPDATE SKIP LOCKED`. История
готовых записей не сканируется каждые 5 секунд. При запуске выполняется идемпотентный
backfill старых фактов. Уникальные ключи защищают задания и уведомления от дублей.
Публикация после commit допускает повтор события с тем же ID; клиент его устраняет.
Email и push не добавлялись.

## 10 Жизненный цикл расписания

Немедленные встречи сохраняют `created → active → finished`. Запланированные
используют `scheduled → active → finished` либо `scheduled → cancelled`.
`scheduledAt` принимается как RFC3339 с timezone и хранится UTC; необязательная
плановая длительность — от 1 до 1440 минут.

Владелец может изменить время только в `scheduled` через `PUT /schedule` и может
начать встречу раньше назначенного времени. Автоматического запуска или жёсткого
завершения по таймеру нет. До старта join означает включение в список будущих
встреч, но не разрешение на медиа. Обновление расписания и старт используют одну
блокировку конференции, поэтому позднее изменение не перезаписывает активную встречу.

## 11 История и списки встреч

`GET /api/v1/me/conferences` поддерживает `view=upcoming|active|past`,
`scope=all|owned|participating`, `status`, `from`, `to`, `cursor` и `limit`.
Фильтры применяются на сервере до пагинации. Порядок —
`COALESCE(finished_at,scheduled_at,created_at) DESC, id DESC`; from/to относятся
к этой же дате. Ожидающие видят свою будущую или активную встречу, но не её историю.

`GET /conferences/:id/history` возвращает закрытую встречу, организатора, время,
длительность, число и первые 100 видимых членств, признак усечения, агрегированные
статусы записей и доступность чата. Остальной список участников доступен по
существующей пагинации. Сводка записей считается из `record`, а не копируется в
конференцию. Воспроизведение использует существующий авторизованный recording API.

## 13 Проверки и гонки данных

До изменений прошли `go test ./...`, `go test -race ./...`, `go vet ./...`,
TypeScript и проверка форматирования. После интеграции прошли серверные тесты,
проверки race/vet, форматирование, сборка frontend, 74 frontend unit/component
теста и 8 браузерных UI-тестов Chromium.

Реальные PostgreSQL, Redis и MinIO использованы для проверки waiting/admit/reject,
переподключения, IDOR, чат-событий между двумя API, повторной отправки, ответов,
edit/delete и mark-read races, финализации и очистки файлов, приватного скачивания,
расписания, курсоров, уведомлений и окончания SSE при истечении токена.
Проверены также быстрая смена admission, повтор job, откат транзакции, ограниченный
fanout, поздние участники и независимость ключей от трёх timezone PostgreSQL.

Сквозная проверка пятого этапа прошла через HTTPS в действующем Docker-окружении
за 26,7 секунды:
расписание и upcoming → напоминание → ожидание после перезагрузки → admit/reject →
две камеры и запись → повтор отправки после потерянного HTTP-ответа без дубля →
ответ, редактирование, удаление и прочтение → файл → рука и реакция → готовая
запись и уведомление → завершение и история с чатом только для чтения.
Отклонённый участник не открыл WebSocket-комнату; обычный участник не увидел его
в списке. Ошибок страницы и сокетов не зафиксировано. Файл размером 1 240 000 байт
прошёл оба прокси: авторизованное скачивание вернуло 200, неподписанный MinIO URL
и запрос отклонённого участника — 403.

Тест запускается с `MEET_STAGE5_DOCKER=true` и конфигурацией
`frontend/playwright.stage5-docker.config.ts` против уже запущенного Compose.
Результаты и проверенные снимки интерфейса находятся в
`frontend/test-results/stage5-docker`. Три созданных тестом пользователя,
конференция, запись, сообщения и приватные файловые префиксы удалены адресно;
пользовательские данные не затронуты.

Опциональные интеграции запускаются с локальными
`RECORDER_STAGE1_TEST_POSTGRES_DSN`, `RECORDER_STAGE2_TEST_REDIS_ADDR` и
`RECORDER_STAGE5_CHAT_E2E=true`. Тесты создают собственные случайные базы и Redis
namespaces; проверки чата в MinIO используют случайный префикс вложений тестовой
конференции в локальном бакете и удаляют только этот префикс.

## 14 Проверки под всплеском нагрузки

Это локальные smoke-измерения, не оценка производственной ёмкости.

| Проверка | Результат одного итогового локального прогона |

| 1500 chat/reaction events и 20 signaling exchanges | p50 2,72 мс, p95 22,85 мс, максимум 36,60 мс; соединения сохранены |
| 80 параллельных HTTP send | 55 приняты, 25 ограничены; критичный снимок доставлен за 159,52 мс |

| 1200 встреч после ANALYZE | Страница 20 строк: 0,049 мс; индекс порядка и индекс членства |

Двенадцать параллельных повторов сообщения, продвижений read state и финализаций
не создают дублей и не откатывают состояние. Сводка истории выполняет фиксированное
число запросов, без дополнительного запроса на каждого участника или запись.

## 15 Регрессия видеосвязи и записи

Проверен SFU с 2, 3 и 5 участниками под race detector: пакеты доставлены без
зафиксированных потерь очереди, после завершения ресурсы освобождены. Браузерная
проверка с новой страницей подтверждает аудио, видео, смену устройств, экран,
модерацию и восстановление медиа после переподключения.

Реальный composite recording test проверил сетку и экран, смешанное аудио,
FFmpeg, ffprobe, закрытый MinIO, lease fencing, восстановление записи и

Проверены 45 декодированных кадров и аудиодорожка; одновременно наблюдался один FFmpeg.

Дополнительно повторена браузерная проверка всей цепочки в Docker с тремя

В сквозной проверке Stage 5 видеопоток продолжался во время работы чата, файлов

и не гарантия производительности. Запись дошла до готовности и появилась в истории.

## 16 Проверка безопасности

Ожидающие, отклонённые, исключённые и посторонние пользователи не получают чат,
файлы, закрытую историю или media ticket. Права проверяются на сервере и повторно
при адресации событий; новый WebSocket проверяет также актуальный начальный снимок.
UUID-формы нормализуются до построения ключей лимитов.

HTML из сообщений отображается как текст. Имена и ключи файлов не управляют путями.
Тело загрузки, количество файлов, очередь и число параллельных загрузок ограничены.
Чат отключает SQL-логирование, которое могло бы раскрыть параметры при ошибках;
HTTP-логи не содержат тела запроса и query string. Приватные ответы имеют no-store.
Токены уведомлений не передаются в URL. Чтение уведомлений проверяет владельца.

Состояние комнаты фильтруется отдельно для каждого получателя; обычный участник
не видит очередь ожидания. Чужой пользователь не может израсходовать общий лимит
реакций конференции. Подписанная ссылка не заменяет проверку доступа при её выдаче.

## 17 Известные ограничения

- Нет антивирусной проверки и просмотра вложений внутри страницы; файлы скачиваются.
- Уже выданная ссылка на вложение действительна до 5 минут даже после исключения.
  Срок существующих ссылок на записи не менялся этим этапом.
- Удаление сообщения закрывает новые скачивания, но не удаляет уже прикреплённый
  объект из MinIO; требуется будущая политика хранения и юридического удаления.
- Чат использует восстанавливаемую доставку через Redis, не отдельный надёжный
  журнал всех WebSocket-событий. Возможна задержка до следующего обновления списка.
- Напоминание приходит только если фоновый обработчик работает в 15-минутном окне;
  большой backlog увеличивает задержку. Повторный запуск не дублирует уведомления.
- Записи о готовности не рассылаются задним числом участникам, допущенным после
  готовности записи; они видят доступные записи через историю.
- Руки не являются историческими данными: Redis loss или часовой TTL их очищает.
- Постоянные данные и обработанные notification jobs пока не имеют автоматической
  политики архивирования. Масштабные квоты и длительные нагрузочные тесты не входят
  в этот этап.
- Проверки браузерного медиа выполнены в Chromium с тестовыми устройствами.
  Они не подтверждают работу физических устройств и Firefox на всех конфигурациях.

## 18 Рекомендации для следующего этапа

Для отдельного этапа 6 полезны TURN и проверка реальных сетей, метрики очередей
и задержек, долговременный нагрузочный тест, политика хранения и очистки истории,
антивирусная обработка файлов и эксплуатационные лимиты. После выбора требований
можно добавить email/push, календарь и расшифровку. Ни одна из этих функций
не запускается автоматически в рамках текущей работы.
