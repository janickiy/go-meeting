# Meet: React + TypeScript + Vite

Интерфейс находится в `frontend/` и использует Stage 1 API, Stage 2 realtime и Stage 3 SFU.
Recorder pipeline не меняется. В production-сборке нет
демонстрационных пользователей, конференций или подменённых API-ответов.

## Реализовано

- Приветственный экран по приложенному дизайну; адаптивная вёрстка.
- Регистрация, автоматический вход после регистрации, экран успеха, вход/выход.
- Восстановление текущей сессии через `/auth/me`, обработка истечения JWT.
- Личный кабинет, список конференций, фильтр статуса и поиск по загруженным страницам.
- Создание конференции, ссылка-приглашение, копирование и открытие email-черновика.
- Присоединение по приглашению, join/leave/rejoin, список участников с пагинацией.
- Начало/завершение/отмена для владельца, подтверждение закрытия встречи.
- Настройки с реальными данными аккаунта в режиме чтения.
- Клавиатурное управление модальными окнами, видимые состояния загрузки и ошибок.
- После join: WebSocket presence, число вкладок и reconnect.
- Минимальная медиа-панель SFU: явное включение камеры/микрофона, локальное preview,
  удалённые audio/video, состояния соединения и отключение медиа.

Описание, планирование, автоматическая запись, восстановление пароля,
редактирование профиля и серверная отправка email пока не реализованы.
Интерфейс не имитирует их работу: неподдерживаемые поля отключены/снабжены пояснениями.
Общий раздел записей остаётся поясняющим экраном. Внутри конференции Stage 4
показывает её защищённую историю записей, индикатор, кнопки владельца и подписанные
ссылки на MP4/превью. Публичный legacy recorder API не используется как личная
библиотека пользователя и не раскрывает composite-записи конференций.
Прежний список участников показывает membership. Новый блок «Связь с участниками»
показывает реальный presence и connectionId; это не состояние подключения камеры.
Контракты presence: [Stage 2 Realtime](realtime.md).
Медиа-контракт, ICE/NAT и проверки: [Stage 3 SFU](media-sfu.md).
Устройства, экран, модерация и запись: [Stage 4 Recording](conference-recording.md).
Прежняя P2P-проверка убрана из интерфейса; production media проходит только через worker.

Камера и микрофон никогда не включаются при открытии страницы или автоматическом
reconnect. После потери WebSocket устройства освобождаются; новое подключение медиа
требует нажатия кнопки. Нужен HTTPS или localhost. Browser receiver track ID может
отличаться от SDP track ID, поэтому клиент связывает треки по доверенным streamId
и kind, сохраняя server track ID для lifecycle. На этапе 3 один источник каждого kind.

## Docker

Из корня проекта:

```bash
docker compose up -d --build media-worker api frontend https
```

- UI: `http://localhost:5173` (только loopback; `FRONTEND_HOST_PORT` меняет порт).
- Общий HTTPS origin: `https://localhost:18482` (существующий локальный сертификат).
- Прямой API остаётся на `http://localhost:8085`.
- `/api/`, `/debug/`, `/health` и `/recordings/` на HTTPS сохраняют прежнее назначение.
- UI deep links обслуживаются через SPA fallback; API-ошибки не превращаются в HTML.

При изменении только конфига HTTPS нужен `docker compose exec https nginx -s reload`.
Сервис `frontend` не получает корневой `.env` и секрет JWT; он раздаёт статические файлы
и проксирует `/api/` на `API_UPSTREAM` (по умолчанию `api:8085`). Файлы шрифтов локальные.
Защита CSP применяется к production-интерфейсу; dev-сервер предназначен только для разработки.

Важно: при пустом `HTTP_TRUSTED_PROXIES` API намеренно не доверяет forwarded-заголовкам.
Тогда rate limiting на общем reverse proxy считает клиентов по адресу proxy.
Для deployment укажите реальные IP/CIDR доверенных proxy; не используйте `0.0.0.0/0`.
Эта настройка не менялась автоматически.

## Разработка

Нужен Node.js 22.22.2+ либо 24.15+ LTS; Docker использует Node 24.

```bash
cd frontend
npm ci
npm run dev
```

Перед запуском dev-сервера освободите порт 5173 или используйте `npm run dev -- --port 5174`.
Vite проксирует API на `http://127.0.0.1:8085`; `API_PROXY_TARGET` меняет только серверный
dev proxy, не публикуя конфигурацию/секреты в клиентском JavaScript.

```bash
npm run build
npm run test
npx playwright install chromium firefox
npm run test:e2e
npm run test:e2e:all
```

Vitest проверяет API-контракт, безопасную навигацию, Unicode-длину пароля, хранение сессии
и клавиатурное управление. Playwright проверяет основные экраны и жизненный цикл
с изолированными тестовыми API-ответами; конфигурации предусмотрены для Chromium и Firefox.
Скриншоты/trace находятся в `frontend/test-results/`, не коммитятся.

Для проверки UI с настоящими Go handlers и PostgreSQL есть opt-in тест из корня:

```bash
RECORDER_FRONTEND_E2E=true \
RECORDER_STAGE1_TEST_POSTGRES_DSN='postgres://go_recorder:go_recorder_pass@127.0.0.1:5433/go_recorder?sslmode=disable' \
go test ./tests/integration -run '^TestFrontendPostgres$' -count=1 -v
```

Тест создаёт случайную отдельную БД, применяет реальные миграции, поднимает временный
Go HTTP сервер и Vite на 5175, проверяет двух пользователей/приглашение/завершение
в Chromium. После проверки удаляется **только созданная тестом БД**. Пользовательская
БД, записи, MinIO и RabbitMQ не затрагиваются. Тест не проверяет Redis rate limiting.

`test:e2e` использует Chromium; `test:e2e:all` также запускает Firefox. На этом Mac
автоматический Firefox не стартует: ОС возвращает `Could not find profile folder`
для изолированного Playwright-браузера. Это похоже на [известную проблему macOS/Playwright](https://github.com/microsoft/playwright/issues/42768).
Проверка Firefox здесь не подтверждена; профиль пользовательского браузера и разрешения
macOS не изменялись. Полный набор можно запускать в совместимом окружении/CI.

## Сессия и контракты

- JWT хранится в `sessionStorage` текущей вкладки, не в `localStorage`; пароли не сохраняются.
  Это не HttpOnly cookie: XSS остаётся риском. Не добавляйте недоверенный HTML/inline script.
- При блокировке storage вход работает в памяти до обновления страницы.
- Срок сессии — один час. Refresh tokens нет; после истечения нужен новый вход.
- Logout удаляет локальный токен/кэш даже при сетевой ошибке. Сервер не отзывает JWT.
- Bearer не отправляется на публичные login/register и никогда — на сторонние origin.
- Redirect после входа разрешён только на локальные страницы приложения.
- Создание отправляет только `{ title }`: `ownerId`, описание, роли и запись не подделываются.
- Пароль: 8–128 Unicode-символов, без обязательных цифр, заглавных букв и спецсимволов.
  Frontend и backend считают длину одинаково; пароли не обрезаются и не нормализуются.
- Политика прав остаётся серверной; скрытие кнопок не заменяет авторизацию API.
- Polling 10–15 секунд остаётся резервом для REST страниц. Realtime обновляется
  через WebSocket; закрытие страницы/выход отменяет запросы и закрывает socket.
- Ссылки `/i/:code` используют origin открытого интерфейса. Участнику нужен аккаунт;
  приглашение сохраняется при переходе через регистрацию/вход.
- Поиск и вкладки фильтруют загруженные страницы, дополнительные страницы доступны кнопкой.
